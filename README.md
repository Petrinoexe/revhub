# revhub

Мини-панель для сети «хаб + выходные»: выходные сами инициируют туннель до
хаба, а хаб раздаёт через них клиентский трафик. VLESS и WireGuard на вход, VLESS /
WireGuard / обратный WireGuard — на транспорт между узлами.

Не форк 3x-ui. Модель данных — единственный источник конфигов: панель рендерит
артефакты, проверяет их `xray -test` и применяет с откатом.

## Что умеет

**Панель**
- вход по паролю (PBKDF2-HMAC-SHA256, подписанная cookie, лимит попыток);
  подписка `/sub/<token>` остаётся публичной — клиенты обновляют её сами;
- карточный UI без горизонтального скролла, тёмная тема, без сборки и CDN;
- адрес прослушивания — свойство состояния (`panel.listen`), а не флага юнита:
  либо `127.0.0.1` (доступ через ssh-туннель), либо адрес WireGuard-интерфейса
  (`10.88.0.1`) — тогда панель не торчит в интернет. Меняется во вкладке
  **Панель** или из CLI:

  ```bash
  revhub panel                    # что слушает и какие есть варианты
  revhub panel set wg             # на адрес WireGuard-интерфейса (или wg:<тег>)
  revhub panel localhost          # назад на петлю
  revhub panel set 10.88.0.1:2096 # явный адрес (есть --port N, --dry-run)
  ```

  Смена адреса = перезапуск юнита: при активном юните CLI сам делает
  `systemctl stop`, пишет состояние и `systemctl start` (живая панель иначе
  пересохранила бы состояние со старым адресом).

- **Открыть панель в интернет** (осознанно): `revhub panel expose` или галочка
  «доступна из интернета» во вкладке **Панель**. Адрес становится
  `0.0.0.0:2096`, флаг `panel.expose=true`, и `apply` открывает TCP-порт в
  `ufw`/`firewalld` на узле панели. Без флага панель не встанет ни на `0.0.0.0`,
  ни на публичный IP — валидация отвергнет адрес с подсказкой.
  Перед этим включи TLS (`revhub install --panel-tls`: домен или IP-сертификат
  Let's Encrypt) — иначе пароль и cookie идут открытым текстом. Если сервер за
  NAT, порт нужно пробросить ещё и там; `revhub panel` показывает,
  включён ли TLS.
  Обратно: `revhub panel hide` (петля) или `revhub panel set wg` (только VPN).

**DNS инфраструктуры**
- вкладка **DNS** задаёт корневой домен (зону), имя панели, TTL и upstream'ы;
- панель **не резолвит сама**: она рендерит конфиг dnsmasq
  (`/etc/dnsmasq.d/revhub.conf`) и файл зоны (`/etc/revhub/dns-hosts`), а
  `apply.sh` привозит их на узел и перезапускает/перечитывает сервис;
- dnsmasq слушает адрес хаба в инфра-сети (`10.89.0.1`, `bind-dynamic`), зона
  авторитетна (`local=/<зона>/`), в неё попадают имена инфра-пиров и панели;
- клиентские DNS-запросы приходят на этот адрес через Xray: ответы из
  `10.89.0.0/24` уходят в инфраструктуру, остальные имена резолвятся публичными
  DNS через выбранный выходной туннель (источник — адрес конца туннеля);
- клиентам адрес резолвера подставляется в подписку (`DNS = 10.89.0.1`).

**Клиенты**
- VLESS-инбаунды: `tcp`, `ws`, `xhttp`; security — `tls` или `reality`;
- TLS: `acme` по домену, `acmeip` — сертификат Let's Encrypt на голый IP
  (shortlived, ~6 дней), `selfsigned` на IP с пином, `file` — свои файлы;
- UUID, срок, квота, привязка к инбаундам, подписка `/sub/<token>`.
- WireGuard-инбаунды — **ядерный** `wg-quick` (UDP `51820` по умолчанию, один
  интерфейс `wgc-<тег>` на инбаунд): все клиенты в одной подсети, видят друг
  друга, наружу выходят NAT'ом этого узла или в туннель. Куда именно —
  настраивается во вкладке **«Маршруты»**, в карточке «выход клиентских сетей»:
  строка на каждую клиентскую сеть, выбор «напрямую» либо «через туннель».
  В карточке инбаунда выхода нет: инбаунд отвечает за свою сеть, а маршрут —
  отдельная сущность. Ключи и адреса у клиентов те же, что в подписке.
  Отметь VLESS и WireGuard в карточке клиента и сохрани. Панель заполнит UUID,
  токен подписки, адрес и ключи WireGuard. Кнопка `sub` открывает общую
  подписку с `vless://` и `wireguard://` (формат v2rayN), а `wg` рядом
  скачивает **стандартный конфиг WireGuard** — `alice-revhub-wg.conf` в формате
  wg-quick: `[Interface]` с адресом клиента, DNS инбаунда и MTU 1420, `[Peer]`
  с публичным ключом сервера, preshared-ключом, `AllowedIPs = 0.0.0.0/0` и
  `PersistentKeepalive = 25`. Если WireGuard-инбаундов несколько, панель
  показывает их в диалоге с предпросмотром файла. Для подключения примени
  сгенерированный конфиг Xray на узле и открой входящий UDP-порт.

**Узлы и туннели**
- `wg` (прямой), `wg-reverse` (выходной за NAT), `vless`;
- добавление хоста по SSH (пароль или ключ): панель сама ставит ядро и
  wireguard, кладёт файлы, применяет и **проверяет** результат на узле;
- мониторинг раз в 20 с: живой ли SSH, задержка, возраст handshake WG,
  через что ходим — `tunnel` или `direct`;
- управление сначала по WG-туннелю, напрямую — только если туннель лёг.

**Маршрутизация**
- упорядоченные правила (user / inbound / domain / ip / port / network) →
  `direct`, `block` или `tun:<имя>`; первый матч выигрывает;
- dry-run: «этот клиент с таким доменом пойдёт туда, и вот какие правила выше
  могут его перехватить».

**Сохранение = применение.** Отдельной вкладки рендера нет: кнопка
«Сохранить» пишет состояние, сразу рендерит артефакты и применяет их — на
сервере панели через `sudo -n revhub apply-local` (правило sudoers ставит
установщик), на выходных узлах по SSH. Индикатор в шапке показывает результат:
`✓ применено` / `✗ не применилось` (клик — подробности). Нужна установка без
применения (отладка) — `revhub serve --apply off`.

Вместе с конфигом применение открывает порты в `ufw`/`firewalld`, если firewall
активен: иначе свежий VPS молча не пускает клиентов.

Проверки на месте:

- **🩺 диагностика узла** — работает ли `xray`, совпадает ли конфиг на узле с
  тем, что собрала панель, слушаются ли порты, что с firewall и WG, есть ли
  ошибки в журнале. Пункт «конфиг ядра на узле» с расхождением sha256 = на узел
  не доехали настройки.
- **📶 пинг по туннелю** (вкладка «Туннели») — рукопожатие WG, пинг дальнего
  конца по интерфейсу туннеля и пинг указанного хоста (по умолчанию 1.1.1.1)
  через выходной узел: проверяет NAT и forwarding на нём.

### Клиентский инбаунд через выходной туннель

1. В поле **Где слушает инбаунд** выбери сервер, к которому подключается клиент.
   Для цепочки «клиент → хаб → выходной» это хаб, то есть начало туннеля.
2. В **Маршрутах** выбери этот инбаунд и исходящий `tun:<имя>`. Поставь правило
   выше общих правил, которые могут совпасть раньше. Для всего трафика инбаунда
   оставь поля пользователя, назначения и сети пустыми.
3. Сохрани — панель применит конфиг сама. Если в шапке `✗`, нажми **🩺** на
   узле: он покажет, что именно не сошлось (не запущено ядро, старый конфиг,
   закрытый порт, нет интерфейса). Затем **📶** в карточке туннеля — пинг
   дальнего конца и хоста через выходной.
   Входящий UDP-порт WireGuard клиента и порт межузлового WG должны различаться,
   если оба слушают на одном хосте. Доступность SSH (`● SSH доступен`) — это
   только SSH, она не говорит о работоспособности туннеля.

Для VLESS на сервере панели можно выбрать **TLS → Сертификат панели**. При
обычной установке локальный узел имеет ID `node-1`. Для ручного запуска с другим
ID передай `revhub serve --local-node <id>` вместе с флагами TLS. Сертификат
используется с существующих путей и не копируется на выходные узлы.

## Установка

Одна команда, дальше вопросы:

```bash
curl -fsSL https://raw.githubusercontent.com/Petrinoexe/revhub/master/install.sh | bash
```

Скрипт спросит всего четыре вещи (Enter — согласиться с предложенным):

1. **публичный IP** — определит сам и покажет на подтверждение;
2. **порт панели** (по умолчанию 2096);
3. **TLS панели**: домен через Let's Encrypt · IP через Let's Encrypt ·
   самоподписанный на IP · без TLS (панель только с localhost);
4. подтверждение.

Панель ставится **пустой**: в состоянии только карточка этого хоста —
инбаунды, туннели, клиентов и правила добавляешь в UI.

Дальше делает всё сам: зависимости (`curl`, `ca-certificates`, `wireguard-tools`,
`nftables`), ядро xray, сертификат, состояние, админа и первого клиента,
systemd-юниты (`xray.service` — со своим конфигом, `revhub.service`), правило
`sudo` для применения конфига, применение конфига и запуск сервиса. В конце
печатает **адрес входа, логин и пароль**
(и пин сертификата, если он самоподписанный).

Если установка или обновление уже проходили раньше и в логах было
`Unit xray.service not found`, достаточно выполнить один раз:

```bash
sudo revhub repair
```

Он ставит юнит xray (прежний, если был, сохраняет в
`/etc/revhub/xray.service.revhub-backup`), правило sudo для панели и применяет
конфиг. Состояние, пароль и TLS не трогает.

Бинарь не скачивается из релиза, а собирается на месте: скрипт делает
`git clone` репозитория и `go build` (Go поставит сам, если его нет — это ~200 МБ
и минута). При повторном запуске выбери **1 — обновить**: настройки, пароль,
порт и сертификаты не пересоздаются, а системная часть (юнит xray, правило sudo,
применение конфига) синхронизируется через `revhub repair`. Старый бинарь и архив
конфигурации сохраняются в `/etc/revhub/update-backup-*`. Если перезапуск не
удастся, скрипт восстанавливает старый бинарь; архив настроек остаётся для
ручного восстановления. Для обновления из готового клона сначала обнови сам
клон: скрипт собирает имеющиеся в текущем каталоге исходники, а не делает pull.

Репозиторий приватный, поэтому клону нужны креды — либо запускай установщик из
готового клона (`sudo bash install.sh`), либо передай адрес с доступом:
`REVHUB_GIT_URL=git@github.com:Petrinoexe/revhub.git` (SSH-ключ) или
`REVHUB_GIT_URL=https://<token>@github.com/Petrinoexe/revhub.git` (токен).
Ещё можно подложить готовый бинарь: `REVHUB_LOCAL_BIN=./revhub`.

| TLS | Что нужно | Кому подходит |
|---|---|---|
| домен | домен + свободный :80 (HTTP-01) или DNS-01 с токеном провайдера | постоянный узел с доменом |
| IP (Let's Encrypt) | публичный IP + **постоянно** свободный :80 | узел без домена, но с открытым 80 |
| IP (самоподписанный) | ничего | узел за NAT или с закрытым 80 (клиенту `allowInsecure`/пин) |
| без TLS | ничего | панель только через `ssh -L`, VLESS виден DPI |

`make release` → `dist/revhub-linux-{amd64,arm64,armv7}` собирает артефакты
локально (для релиза на GitHub), но установщику они больше не нужны.
Автоматизация без вопросов: `revhub install --host … --tls … --panel-tls`
(см. раздел CLI) — это тот же движок, который вызывает `install.sh`.


Ключи `revhub install` (нужны для автоматизации, интерактивный установщик
вызывает их сам): `--panel-tls` (HTTPS для панели), `--with-inbound` (создать
стартовый VLESS-инбаунд и клиента; по умолчанию панель пустая), `--port`
(порт VLESS, только вместе с `--with-inbound`),
`--acme http|dns|off`, `--acme-http-port`, `--cert/--key` (свои файлы),
`--dry-run` (файлы писать, системные команды не выполнять), `--no-apply`,
`--skip-packages`, `--print-password`.

## Локальная сборка (разработка)

```bash
make build                                   # ./revhub
./revhub demo --state demo-state.json        # демо: хаб + выходной, TLS по IP
./revhub serve --state demo-state.json       # http://127.0.0.1:2096
./revhub passwd --state demo-state.json      # пароль панели (спросит дважды)
./revhub serve --noauth                      # UI без пароля, только loopback
make verify                                  # render + xray -test по всем узлам
make test                                    # go test ./...
```

Нужен Go 1.26+ для сборки (так требует `golang.org/x/crypto` в SSH-клиенте);
сам бинарь статический, зависимостей нет.

## CLI

```
revhub serve    [--addr 127.0.0.1:2096] [--state state.json] [--out out]
                [--noauth] [--tls-cert FILE --tls-key FILE]
revhub install  --host <ip|домен> [--tls domain|ip-le|ip|reality|none]
                [--domain d] [--email e] [--panel-tls] [--dry-run]
revhub tls selfsigned --hosts ip[,домен] [--out DIR] [--days N]
revhub tls info       --cert FILE [--json]
revhub tls acme       --domain d --email e [--method http|dns] [--dns dns_cf]
revhub passwd   [--state state.json] [--user admin] [--random --password-file f]
revhub render   --node <id> [--state state.json] [--out out]
revhub validate [--state state.json]
revhub demo     [--state demo-state.json]
revhub version
```

## Чего пока нет

- мультиадмин и роли: один админ;
- отзыв сессии = смена пароля (списка сессий нет);
- ротация ключа хоста SSH из UI (TOFU: первый ключ запоминается);
- hot-reload сертификата: продление ACME перезапускает xray;
- биллинг, Telegram-бот, «все протоколы как в 3x-ui» — сознательно.
