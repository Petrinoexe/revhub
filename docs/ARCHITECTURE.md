# revhub — архитектура

Мини-панель для сети «хаб + выходные», где выходные сами инициируют туннели.
Одна и та же панель ставится на любой узел: входной, выходной или оба сразу.

## 1. Две плоскости

Ключевое проектное решение: в системе **две независимые плоскости**, и они
соединяются ровно в одном месте.

| Плоскость | Кто исполняет | Что знает | Чего не знает |
|---|---|---|---|
| Клиентская | xray (VLESS/REALITY/XHTTP) | про пользователей, sniffing, свои правила | про маршруты ядра |
| Туннельная | ядро Linux (WireGuard) | про интерфейсы, таблицы, метки | про xray и его правила |

Клей — **fwmark**. xray для исходящего, который должен уйти в туннель, ставит
метку на сокет (`streamSettings.sockopt.mark`), в ядре лежит правило
`ip rule add fwmark N lookup T` и таблица T с `default dev wgX`. Убрали метку —
трафик вернулся в main. Никаких правок основной таблицы маршрутизации.

Что это даёт: `wg-quick` не перехватывает default (у всех интерфейсов
`Table = off`), собственный трафик узла (ssh, apt, DNS, резолв endpoint'ов)
никогда не попадает в туннель, а откат любого туннеля — это `wg-quick down`
без последствий для остальных.

## 2. Что делает панель

Панель **никогда не правит живой конфиг руками**. Она рендерит артефакты из
модели (см. `DATA-MODEL.md`) и применяет их конвейером:

```
render → validate (xray -test) → backup last-good → atomic install → reload → verify
```

Любой шаг падает — на диске остаётся previous, `rollback.sh` возвращает
предыдущий набор одной командой. Это требование к каждой фиче, а не «потом
допишем».

## 3. Модель ролей

Узел (`Node`) имеет роль `entry`, `exit` или `both`. Универсальность
достигается тем, что **протоколы не привязаны к роли**: один и тот же
`Inbound` (приём) и один и тот же `Tunnel` (транспорт до другого узла)
рендерится на любом узле в зависимости от того, какой он конец туннеля.

Туннель задаётся парой узлов и видом:

| Kind | Кто слушает (ListenPort) | Кто дозванивается (Endpoint) | Трафик |
|---|---|---|---|
| `wg` | дальний (exit) | ближний (hub) | from → to |
| `wg-reverse` | ближний (hub) | дальний (exit) | from → to |
| `vless` | дальний (exit) | ближний (hub) — как клиент VLESS | from → to |

Направление трафика от `Kind` не зависит: во всех трёх случаях `From`
отправляет, `To` выпускает в интернет. Меняется только сторона handshake'а —
именно это и нужно: на `wg-reverse` выходной может жить за NAT/CGNAT.

## 4. Артефакты узла

Для каждого узла панель рендерит:

```
out/<node>/xray.json          — конфиг ядра (инбаунды клиентов, аутбаунды, правила)
out/<node>/wg-<tunnel>.conf   — интерфейсы WireGuard (Table = off всегда)
out/<node>/apply.sh           — применить: wg-quick down/up, ip rule, xray -test, reload
out/<node>/rollback.sh        — вернуть предыдущий набор
out/<node>/manifest.json      — что именно было применено и когда
```

## 5. Маршрутизация

Правила (`Rule`) — упорядоченный список, порядок = приоритет, первый матч
выигрывает. Матч: `user`, `inbound`, `domain`, `ip`, `port`, `network`.
Цель — тег исходящего: `direct`, `block` или `tun:<имя туннеля>`.

UI показывает для каждой строки, сколько клиентов/трафика она получит, и даёт
dry-run: «этот клиент с таким доменом пойдёт в такой исходящий, потому что
сработало правило №N». Ровер правил повторяет логику xray (первый матч),
поэтому проверка не врёт на структуре — но `geoip:`/`geosite:` локально не
раскрываются, и в ответе это указывается явно.

## 6. Границы MVP

- Один узел на процесс: панель управляет тем узлом, на котором стоит.
  Управление чужими узлами (агент) — следующий этап, API под него уже
  разделён: `render` возвращает артефакты для конкретного `nodeID`.
- Хранилище — один JSON-файл с атомарной записью и одним писателем.
  Обоснование и точка перехода на SQLite — `DECISIONS.md`.
- Без биллинга, Telegram-бота и мультиадминки сознательно.

## 7. Узлы: SSH, первичная установка, мониторинг

Панель стоит только на хабе. Остальные хосты — **управляемые узлы**: у них нет
ни панели, ни состояния, только ядро и конфиги, которые панель туда положила.

Поток «добавить хост» (вкладка «Узлы», кнопка «Поставить и связать»):

1. создаётся `Node` (адрес, SSH-параметры) и `Tunnel` нужного вида
   (`wg` / `wg-reverse` / `vless`) с ключами, подсетью и меткой;
2. секрет SSH кладётся в `secrets.json` (0600) — в состоянии его нет;
3. рендерятся артефакты обеих сторон: для выходного и для хаба;
4. по SSH на выходной ставятся пакеты (`wireguard-tools`, `nftables`), при
   необходимости ядро xray, юнит, файлы узла и выполняется `apply.sh`;
5. результат проверяется на месте: `systemctl is-active xray`, `wg show`,
   `curl ifconfig.me` — то есть узел обязан сам подтвердить, что вышел в сеть;
6. узел получает статус, отпечаток ключа SSH (TOFU) и время установки.

Ручная связка двух хостов остаётся: туннель можно создать в модели и нажать
⚙ на узле — панель поставит на него ровно то, что описано в модели.

### Как панель ходит на узел

Правило: **сначала через WG-туннель, напрямую — только если туннеля нет или он
умер**. Для этого `wg-quick` на стороне `from` добавляет host-route до дальнего
конца (`ip route replace 10.77.N.2/32 dev wg-X`), не задевая остальной трафик.
Адреса-кандидаты считает `internal/mgmt`: сначала адрес в туннеле, потом
публичный; первый живой выигрывает, и в состоянии записывается `mgmt_via`.

### Мониторинг

Фоновый цикл раз в 20 секунд проверяет каждый узел: TCP-коннект **и SSH-баннер**
(коннект сам по себе врёт — перехватчик отвечает SYN-ACK на что угодно), плюс
возраст последнего handshake WG через `wg show <if> latest-handshakes`.
Результат: `status` (alive/dead/unknown), `latency_ms`, `handshake_age`,
`last_check`, `mgmt_via`. Кнопка 🔍 делает ту же проверку немедленно.
